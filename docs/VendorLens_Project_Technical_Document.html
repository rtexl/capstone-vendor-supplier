1. Executive summary

VendorLens AI is a full-stack supplier onboarding and review application. It replaces a fragmented email-and-spreadsheet process with a controlled workflow in which suppliers submit structured details and evidence, AI assists with extraction and evidence discovery, deterministic policy checks expose gaps, a human reviewer remains responsible for every final decision, and approved data is transferred to a separately bounded mock ERP service.

1.1 Business problem

Supplier onboarding normally combines identity data, tax and bank evidence, category-specific controls, insurance, security questionnaires, and human judgment. The process is slow when evidence arrives through separate channels, difficult to audit when reviewers cannot trace a value to its source, and risky when an automated system is allowed to infer or approve beyond the evidence.

1.2 Proposed solution

VendorLens provides three role-specific workspaces:

  • Supplier portal: account registration, India-based business details, category selection, dynamic evidence checklist, pre-acceptance upload validation, OCR reliability and extracted-value preview, submission, correction/resubmission, and a scoped onboarding assistant.
  • Reviewer workbench: case list, attention/matched/verified/flagged requirement queues, original evidence, extracted values with page references and confidence, OCR correction, individual or guarded bulk confirmation, AI-assisted flag-reason drafting, grounded case chat, approval or rejection, and ERP record retrieval.
  • Administrator workspace: profile maintenance and aggregate AI/OCR/ERP observability.

1.3 Architectural position

Core design principle: AI supports document understanding and retrieval; it does not own the approval decision. Approval is permitted only when every persisted compliance result is PASS, and an explicit reviewer action completes the decision and ERP handoff.

The implementation combines React and Material UI, a FastAPI service layer, PostgreSQL for durable business state and audit records, local file storage for document originals, ChromaDB for supplier-scoped vectors, an OpenRouter-or-Azure OpenAI provider boundary, and a separate JSON-RPC mock ERP MCP service. Docker Compose assembles the local system.

1.4 Current maturity

The repository represents a feature-rich capstone/demo implementation rather than a production procurement platform. It includes schema migrations through revision 0017_erp_identifier_separation, 92 backend test functions across 21 test modules, configurable staff authentication, staged upload validation, local OCR with reliability scoring, privacy-conscious telemetry, guarded bulk review, and end-to-end workflow controls. Production use still requires hardened identity, secret management, object storage, network encryption, retention controls, malware scanning, authorization policy, backup/restore procedures, and independent security and regulatory review.

3.3 Important workflow semantics

  • Upload acceptance is not compliance. Pre-acceptance checks reject unreadable, wrong-type, obviously wrong-supplier, incomplete, or very low-quality evidence, but do not establish authenticity or final policy compliance.
  • OCR reliability is triaged. Poor scans are rejected, uncertain scans are accepted only into a manual-attention state, and clear scans still require human comparison before approval.
  • Submission is durable. An AI/provider failure is recorded for review but does not roll back the supplier submission.
  • Requirements are frozen. The selected checklist is saved as a requirements snapshot on first submission, protecting the case from silent future catalogue changes.
  • Corrections are bounded. Category/subcategory cannot change during a correction cycle. Disputed evidence can be replaced and resubmitted.
  • Bulk confirmation is conservative. Only pending, fully processed requirements with matched checks are eligible; OCR/manual-attention, failed, disputed, and already reviewed items are excluded.
  • Finalization is guarded. Finalized cases cannot be reprocessed or modified through the normal workflow.

4.3 Key architectural decisions

  • PostgreSQL is the source of truth for workflow and audit data; ChromaDB is a derived retrieval index.
  • Text extraction is synchronous at upload so unreadable evidence is rejected early and visibly.
  • AI processing is invoked after submission as an in-process FastAPI background task; manual reviewer processing/retry is also available.
  • Provider selection is exclusive and configuration-based. A failed OpenRouter request does not silently fail over to Azure.
  • AI prompts are versioned text files and run records persist prompt/model/token/latency metadata.
  • ERP creation is deterministic application logic after human approval; an LLM never chooses or executes ERP tools.

Bearer session tokens are stored by role in browser localStorage and attached to API calls. Client guards improve navigation but are not security controls; the API independently applies supplier, reviewer, or administrator dependencies. This local-storage approach is acceptable for a controlled demo but should be replaced or strongly hardened for production because browser script compromise can expose tokens.

5.4 User-experience controls

  • Dynamic checklist entries are derived from the selected subcategory.
  • Each selected file shows an in-progress validation state. A file appears in the checklist only after temporary-stage checks pass; rejection feedback identifies unreadability, wrong type, missing information, identity mismatch, low OCR quality, or validation unavailability.
  • OCR evidence shows a reliability percentage and read-only extracted-value preview. Suppliers replace a file when the preview is wrong; reviewers can correct the value and page against the original.
  • The reviewer workbench groups requirements into needs-attention, matched, verified, and flagged views and exposes Confirm all only for the matched subset.
  • Processing, upload validation, OCR, review, compliance, decision, ERP record, and Vendor ID statuses are shown independently.
  • Original files open through authenticated API endpoints with no-store headers and integrity verification.
  • Assistant output supports Markdown/GFM presentation, while the backend owns content scope and redaction.
  • The Vendor Master supports search, status/category filters, sorting, pagination, full-record retrieval, links back to onboarding evidence, and CSV export of the filtered result set.

6.3 Error and transaction behavior

HTTP errors are normalized to {code, message}; Pydantic validation errors return a stable validation_error body with details. Database sessions are request-scoped. Long AI operations explicitly create and finalize AiRun records, sanitize persisted failure messages, and retain document-level status so partial processing is diagnosable. Submission and AI processing are deliberately decoupled.

6.4 CORS and request metrics

CORS accepts only the configured frontend origin. Middleware records count, latency, status, and in-progress gauges while normalizing UUID path segments to avoid unbounded metric labels. The metrics application is mounted separately at /metrics.

8. Document ingestion, OCR, and revisions

8.1 Staged upload controls

  • Allowed MIME types: PDF, PNG, JPEG, and plain text.
  • Default maximum: 10 MB, enforced by reading at most the limit plus one byte.
  • One active file per supplier and required document type, enforced in the API and database.
  • Bytes are first written under .staging/<supplier UUID>. Text/OCR extraction and configured validation complete before the file is moved to permanent UUID-named storage.
  • With UPLOAD_AI_VALIDATION_ENABLED=true, the service checks detected document type, required extracted fields, and conservative comparisons of legal name, tax reference, bank account, and IFSC against portal values.
  • Wrong-type, missing-field, confident identity-mismatch, unreadable, and poor-quality files return actionable errors, record a sanitized rejection audit, and are deleted from staging. An AI outage returns 503 and does not save the file.
  • When AI validation is disabled for offline development, readability and OCR-quality gates still apply, but the stored validation state is text_only; document-type, field, and identity checks are not performed.
  • Original name is reduced to a basename and retained as metadata; the stored name is a generated UUID plus an allowed extension.
  • Each file receives a SHA-256 digest. Content access recalculates the digest and fails closed on mismatch.
  • Resolved paths must remain under the configured upload root.

8.2 Extraction algorithm

For every PDF/image page
  ├─ read native text
  ├─ measure alphanumeric and word thresholds
  ├─ estimate large-image coverage
  ├─ if native text is weak or page is image-dominant:
  │      run local Tesseract OCR (subject to page cap)
  └─ store [Page N] marker + chosen text

Result method = native | mixed | ocr
Result metadata = page count + OCR page numbers + language + warnings + page quality metrics

Figure 4. Page-selective extraction. Images are treated as one-page visual documents.

8.3 OCR reliability and human review

For OCR-derived evidence, VendorLens calculates an extraction-reliability score from visual clarity (45%), average extracted-field confidence (40%), and required-field coverage (15%). This is explicitly an extraction signal, not an authenticity or fraud score.

Score bandStored statusJourney behavior
0–34poorReject before permanent storage and ask for a sharper, complete, well-lit image.
35–69reviewAccept with every affected value marked for manual attention; supplier sees a read-only preview and the item is excluded from bulk confirmation.
70–100goodAccept without an OCR-quality warning; normal reviewer comparison and compliance gates still apply.

The visual component caps the combined result in its own band, preventing high model confidence from masking a poor or uncertain source image. Reviewers see OCR-derived pages, reliability, extraction confidence, and the original side by side; an audited correction records the previous value, corrected value, source page, previous confidence, and reviewer.

8.5 Failure and retry

A new unreadable or validation-failed upload is not retained as active evidence: its temporary bytes are removed and the supplier receives a safe, specific error. Retry endpoints remain available for previously persisted or operationally failed documents after environment/file issues are resolved. Upload validation, text extraction, structured extraction, and index states remain independent so operators can locate the failed stage.

8.6 Revision model

Before an active document is deleted or successfully replaced, its immutable metadata is inserted into document_revisions. A rejected replacement leaves the current active evidence untouched. Revision numbers increase per supplier/document type. Authenticated supplier or reviewer endpoints can list history and open an active or archived original. Viewing is audited and responses use Cache-Control: private, no-store and X-Content-Type-Options: nosniff.

9. AI processing and retrieval-augmented generation

9.1 Provider selection

When OPENROUTER_API_KEY is non-empty, OpenRouter is used. Otherwise the service requires an Azure OpenAI key and endpoint. Extraction, answer, and embedding models are configured independently. Defaults target gpt-4o-mini and text-embedding-3-small model families. Provider choice is cached for the process lifetime, so configuration changes require restart.

No runtime cross-provider failover. A failed OpenRouter request is surfaced and recorded rather than being retried through Azure. This prevents supplier information from moving silently to another provider because of an outage, bad key, or quota failure.

9.2 Processing pipeline

Readable original text
      │

      │                              (GSTIN, PAN, CIN, email, phone, bank account)
      ▼

9.3 Structured extraction controls

  • The active extraction prompt is extraction-v4; output is parsed into typed Pydantic schemas.
  • The model must use only supplied redacted text, copy values rather than infer them, and return each allow-listed field exactly once.
  • Each non-null value includes page and confidence. Long narratives are rejected in favor of null.
  • Null-like strings are normalized; explicit policy-significant answers such as “None” or “Not applicable” are preserved for selected fields.
  • Canonical selection considers authoritative document types, confidence, and conflicts rather than presenting every duplicate equally.
  • Every run records provider model, prompt version, token counts, latency, redaction summary, document outcomes, field count, chunk count, and errors.

9.4 Chunking and vector isolation

Text is split by [Page N] markers, then tokenized with the active embedding-model encoding (falling back to cl100k_base). Default chunks are 500 tokens with 75-token overlap and never span source pages. Chroma metadata includes supplier, document, page, and chunk identity. Every retrieval query requires the supplier ID before similarity ranking, which is the primary cross-supplier isolation control.

9.5 Cited document Q&A

  1. Redact the reviewer’s question.
  2. Embed the redacted question.
  3. Retrieve up to four supplier-filtered chunks within the default distance threshold of 0.72.
  4. Present short model-facing labels such as chunk_1.
  5. Require the answer model to return an answer, information_found, and exact supporting labels.
  6. Validate citations against retrieved evidence. If evidence is absent, return the exact guarded response: “Information not found in uploaded supplier documents.”

10.2 Evidence definition

Each requirement contains a business label, rationale, accepted evidence description, required fields, exactly two checks, and a policy-source reference. The catalogue is deterministic JSON derived from 12 synthetic policy texts. At submission the resolved checklist is snapshotted into the supplier record.

10.4 Human-in-the-loop controls

  • Reviewers can verify or dispute selected fields; disputes require a reason.
  • Reviewers can correct a value and page reference. A correction receives confidence 1.0 and audited reviewer identity.
  • Reviewers verify or dispute an entire evidence document. Verifying the document verifies its non-corrected extracted fields.
  • The Confirm all action verifies only pending requirements whose documents and AI extraction are ready, indexing has not failed, and every policy check is matched or already human-verified. Manual-attention/OCR, disputed, failed, and already reviewed items are excluded and the batch is audited.
  • A reviewer may request a flag-reason draft grounded in current findings and policy RAG, but must review or edit and explicitly save the reason.
  • Any field or evidence change recalculates current compliance results.
  • A reviewer still provides an explicit approval or rejection action after compliance is ready.

11. Mock ERP / MCP integration

11.1 Boundary and tools

Docker Compose runs mock-erp-mcp as a separate stateless API process on the internal network. The backend client uses JSON-RPC at /mcp when a URL is configured; local development/tests may call the same tool implementation in process.

ToolPurpose
validate_supplier_recordRequired master fields, India scope, category mapping, IFSC length, duplicate tax/bank checks, optional-field warnings, idempotent replay detection.
create_supplier_recordValidate and insert an active supplier master with a stable 10-digit Vendor ID and distinct ERP-REC-… record ID.
get_supplier_recordRetrieve the created record by Vendor ID.
list_supplier_recordsList downstream records for the reviewer Vendor Master.

11.2 Mapping and provenance

The ERP preview prefers reviewed/corrected evidence for supported fields, falling back to supplier-entered values, and labels each source as system-generated, supplier-entered, reviewed evidence, or unavailable. Category/subcategory remain supplier selections. Three identifiers are deliberately separate: the portal reference (SUP-…) identifies the onboarding case, the ERP record ID (ERP-REC-…) identifies the downstream creation record, and the stable 10-digit Vendor ID is the primary business identifier in the Vendor Master. The stored case retains the final ERP payload and both returned ERP identifiers.

11.3 Approval and retry semantics

Reviewer clicks Approve

      ├─ recompute all compliance results; require all PASS
      ├─ build ERP preview with source map
      ├─ validate_supplier_record
      ├─ create_supplier_record (idempotency key = supplier case ID)

ERP unavailable / validation error → approval remains incomplete → safe retry

Figure 7. Idempotency prevents a repeated approval attempt from creating duplicate downstream records.

11.4 Audit and privacy

Every tool attempt records operation, attempt number, status, latency, safe error code, requested field names, and limited response facts. Raw tax and bank values are deliberately excluded from the integration attempt summaries. Langfuse receives tool outcome metadata when configured.

11.5 Vendor Master journey

Approved ERP records appear in the reviewer-only /review/vendor-master workspace. The SAP-style table is read-only and supports identifier/name search, status and category filters, sorting, pagination, full ERP record retrieval, and a link back to the onboarding case and evidence trail. CSV export includes the currently filtered rows and escapes spreadsheet-formula prefixes in supplier-provided values. Master-data changes remain the responsibility of the downstream ERP rather than VendorLens.

12.2 PII redaction scope

Current regular expressions cover Indian GSTIN, PAN, CIN, email, Indian-format mobile numbers, and 12–18 digit bank account numbers. Values are replaced with stable per-document typed placeholders such as [GSTIN_1]. A local map restores placeholders in structured results after the provider responds.

Residual risk: regex redaction is not a complete sensitive-data discovery system. Names, addresses, unusual phone formats, account numbers outside the pattern, free-form identifiers, and OCR errors may pass through. Production use needs a formal data classification/DLP design, provider agreements, regional controls, and testing against representative documents.

12.3 Audit model

AuditEvent captures business actions; AiRun captures AI operational evidence; ErpToolAttempt captures integration attempts; document and field reviewer columns capture the latest human disposition. Together they answer who/what/when/source questions without exposing extracted document text in general API responses.

12.4 Demo-mode security posture

Reviewer and administrator authentication are disabled by default, enabling one-click role sessions for demonstrations. The database uses a simple Compose credential, traffic is HTTP, metrics and API documentation are public, session tokens live in local storage, and files use a local volume. These are deliberate usability choices for local demonstration, not acceptable production defaults.

13. Observability and quality evaluation

13.1 Health and metrics

GET /api/health checks PostgreSQL with SELECT 1 and calls the Chroma heartbeat. The result is healthy only when both dependencies connect. Prometheus metrics include:

  • HTTP request count, duration, status, and in-progress requests;
  • AI call count/duration and input/output tokens;
  • processing-run outcomes, RAG questions and retrieved-chunk distribution;
  • compliance status counts and supplier decisions;
  • dependency health gauges.

13.2 Administrator observability

The admin API aggregates a configurable time window of provider/model/prompt usage, successes/failures/in-progress runs, tokens, average and P95 latency, question grounding/not-found behavior, retrieval counts, native/OCR document counts, OCR pages, extraction failures, ERP attempts/failures/latency, and recent runs. When configured, read-only Langfuse summaries add trace and observation counts, model cost, and named numeric quality/grounding scores without retrieving captured prompt or output content; the dashboard link is exposed without credentials.

13.3 Langfuse tracing

Tracing is optional and failure-tolerant. Workflow families cover staged upload validation, document extraction, supplier document processing/RAG, supplier/reviewer assistants, reviewer flag-reason drafting, and ERP MCP calls. Content capture defaults false; operational metadata, model, prompt version, token usage, latencies, validation/quality outcomes, release, and a non-reversible supplier subject label support debugging and cost analysis. Telemetry exceptions do not change application behavior.

13.4 Evaluation assets

The repository contains generated evaluation documents, ground truth, and scripts for repeatable extraction/Q&A checks, plus a Promptfoo runbook. Historical project notes report a v3 evaluation of 36/36 field checks and 24/24 Q&A checks with complete citation, not-found, and supplier-isolation accuracy. Those figures are historical evidence rather than a result rerun during this documentation pass; they should be regenerated against any release candidate.

16. Constraints, risks, and production readiness

16.1 Current constraints

  • Synthetic India-only policy, one primary subcategory, and mock downstream integration.
  • Background AI work runs in the API process, without a durable job queue, distributed lock, or worker autoscaling.
  • Local filesystem and embedded Chroma persistence assume a single shared runtime volume.
  • Regex PII redaction and OCR accuracy are document-dependent; the reliability score reduces ingestion risk but is not an authenticity control.
  • Provider/model outputs remain probabilistic even with schemas and prompts; human verification is essential.
  • Demo-mode staff access, browser local-storage tokens, public docs/metrics, and HTTP are not production controls.
  • There is no declared browser end-to-end, load, penetration, accessibility, or disaster-recovery test suite.

16.2 Risk register and recommended treatment

RiskImpactRecommended treatment before production
Weak/demo identity modelUnauthorized staff or session access.OIDC/SAML SSO, MFA, short-lived secure HttpOnly cookies, CSRF strategy, centralized RBAC/ABAC, revocation and login audit.
Supplier documents are sensitivePrivacy, fraud, contractual and regulatory exposure.Encrypted object storage, KMS, malware/CDR scanning, DLP, retention/deletion schedules, legal basis, access review and download watermarking where appropriate.
Incomplete PII detectionSensitive content may reach external AI/telemetry.Formal data inventory, stronger DLP/entity recognition, provider zero-retention terms, regional routing, test corpus and privacy impact assessment.

16.3 Suggested evolution sequence

  1. Security baseline: enterprise identity, TLS, secrets manager, private operational endpoints, object-store encryption and scanning.
  2. Reliability baseline: durable worker queue, job state/retry, managed persistence, backups and restore tests.
  3. Governance baseline: formal policy approvals, retention and privacy controls, model/prompt release management.
  4. Quality baseline: browser E2E, load/security/accessibility tests, expanded OCR and adversarial AI evaluation.
  5. Integration baseline: authenticated enterprise ERP adapter, schemas/contracts, reconciliation, non-repudiation and operational ownership.

  • Restart: docker compose up -d.
  • Rebuild: docker compose up --build -d.
  • Reload backend environment: docker compose up -d --force-recreate backend.
  • Migration state: docker compose exec backend python -m alembic current.

17.3 Diagnostic sequence

  1. Check Compose health and backend logs.
  2. Call /api/health to isolate PostgreSQL/Chroma connectivity.
  3. Use admin observability to locate failed AI runs, models/prompts, OCR failures, and ERP attempts.
  4. Inspect the supplier’s upload-validation status, OCR reliability/details, document review state, AI extraction/index status, last run, and audit events.
  5. For an upload rejection, use its safe issue code/message to distinguish unreadability, wrong type, missing expected fields, identity mismatch, low OCR quality, and provider unavailability; rejected temporary files are not recoverable case evidence.
  6. For OCR failures, verify Tesseract and the configured language pack, then retry eligible persisted text extraction or ask the supplier for a clearer source.
  7. For AI configuration changes, restart the backend because the settings/client are cached.
  8. For ERP failure, fix connectivity/validation and retry approval; the idempotency key makes the create safe.

17.4 Data reset caution

docker compose down -v destroys PostgreSQL, upload, and Chroma volumes. It should be used only when a complete local reset is intended. Ordinary docker compose down preserves the volumes.

Technical conclusion. VendorLens demonstrates a coherent human-in-the-loop onboarding architecture: evidence is ingested with provenance, AI output is bounded and reviewable, policy checks remain explicit, downstream creation is deterministic and idempotent, and operational evidence is retained. Its architecture is suitable for a capstone demonstration and a strong prototype foundation, provided the production-readiness controls in Section 16 are treated as prerequisites for real supplier data.
